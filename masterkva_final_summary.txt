MasterKva — итог по архитектуре v1

## 1) Что это за проект
MasterKva — платформа обучения и диагностики по математике для 1–9 классов.

Цель проекта — не просто выдавать задания, а вести ученика по понятному учебному маршруту:
- диагностика уровня;
- поиск слабых тем;
- объяснение по учебному материалу;
- практика на аналогичных заданиях;
- проверка закрепления навыка;
- переход к следующей теме только после mastery gate.

Проект строится на учебных материалах и визуальных шаблонах, а не на абстрактной генерации задач.

## 2) Что уже есть
- backend и frontend работают;
- есть `backend/data/diagnostic_pool.json`;
- есть `backend/data/visual_topic_map.json`;
- есть `backend/data/curriculum_detailed/`;
- есть `backend/data/lessons/*_ru_adapted.json`;
- исправлен конфликт между диагностикой и практикой;
- после диагностики система ждёт явного продолжения;
- проверены E2E-сценарии через Playwright/Chromium;
- подтверждено, что для ранней арифметики нужен `number_bond`;
- визуалы уже связаны с темами.

## 3) Что в текущем подходе правильно
- разделять диагностику и обучение;
- держать backend главным владельцем образовательной логики;
- отключать доску в диагностике;
- включать доску в обучении;
- не давать LLM самой решать, что считать progress/mastery;
- использовать простую state machine для v1;
- не смешивать тему, навык, вопрос, урок и визуализацию в одну сущность.

## 4) Что сказали внешние модели
### Perplexity
Главная мысль: не переусложнять LLM-слой. Для v1 лучше простая state machine:
- diagnose
- remediate
- practice
- promote

### GPT-5.5
Главная мысль: нужен не набор разрозненных JSON-ов, а единая образовательная схема.
Рекомендован каркас:
- Skill Registry
- Assessment Engine
- Learning Engine
- Visual Engine
- LLM Tutor Layer

GPT-5.5 также отдельно подчеркнул:
- диагностика, remediation и mastery gate не должны смешиваться;
- backend должен решать переходы;
- нужен coverage status по каждому skill;
- текущий diagnostic pool слишком маленький для полной диагностики 1–9.

## 5) Моё дополнение к плану GPT-5.5
Я считаю, что к его архитектуре нужно добавить отдельный слой:

### Skill Contract
Внутри него два блока:
1. coverage — что покрыто и в каком состоянии;
2. error_model — типичные ошибки и что делать дальше.

Это лучше, чем пихать всё в `skill_registry`, потому что:
- `skill_registry` отвечает за то, какие навыки существуют и как они связаны;
- `skill_contract` отвечает за то, как конкретный навык проверять, лечить и показывать.

## 6) Финальная рекомендуемая архитектура v1
### Слои
1. Skill Registry

3. Assessment Engine
4. Learning Engine

6. LLM Tutor Layer

### Что хранит Skill Registry

### Что хранит Skill Contract
- coverage_status

## 7) Правила по фазам
### Diagnosis
- доска off;
- без подсказок;
- backend выбирает вопрос детерминированно;
- ошибка не приводит сразу к уроку.

### Diagnosis review
- показываем результат;
- ждём явного продолжения;
- не начинаем обучение автоматически.

### Remediation
- включаем урок по учебному материалу;
- используем разрешённый visual template;
- объясняем коротко и по шагам.

### Guided practice
- даём похожие задачи того же skill;
- разрешаем ограниченные hints;
- отслеживаем повторяющиеся ошибки.

### Mastery check
- проверяем закрепление;
- если не пройдено — возвращаемся в remediation/practice.

### Promotion
- если skill mastered — переходим дальше;
- если нет — остаёмся или откатываемся к prerequisite.

## 8) Что нужно изменить сразу
- ввести `skill_registry` как единый источник структуры навыков;
- ввести `skill_contract` как слой над registry;
- расширить диагностическое покрытие, потому что текущий пул слишком мал;
- зафиксировать board policy по фазам;
- хранить coverage status по каждому skill;
- для v1 держать переходы детерминированными.

## 9) Что можно отложить
- сложные психометрические модели;
- IRT/BKT;
- генерацию уроков на лету;
- тяжёлую аналитику для учителей;
- сложную автоматическую классификацию всех ошибок через LLM;
- слишком умную универсальную доску.

## 10) Главные риски
- смешать диагностику, урок и practice в одну кучу;
- положиться на LLM как на источник образовательной истины;
- попытаться покрыть всю математику 1–9 без skill map;
- сделать одну универсальную доску вместо набора устойчивых шаблонов;
- считать, что маленький diagnostic pool уже даёт полноценную диагностику.

## 11) Что я считаю правильным планом для v1
- строить систему как простую state machine;
- сделать каркас навыков и контрактов;
- сначала закрыть ядро 1–4 классов, потом расширять 5–9;
- держать доску как поддерживающий визуальный слой;
- LLM использовать как teacher layer, а не как owner логики;
- не спешить с усложнением, пока не покрыто ядро.

## 12) Короткий вывод
Берём план GPT-5.5 за основу, но дополняем его отдельным слоем Skill Contract. Это делает систему чище: registry отвечает за структуру навыков, contract — за диагностику, ошибки, ремедиацию, визуалы и мастерство.
