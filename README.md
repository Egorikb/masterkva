# MasterKva

MasterKva — это система обучения и диагностики по математике для 1–9 классов.

Проект строится как последовательный педагогический маршрут:

1. ученик проходит диагностику;
2. система определяет слабые темы;
3. дальше даётся объяснение по учебному материалу;
4. затем идёт практика;
5. после этого проверяется усвоение;
6. при необходимости ученик получает следующий шаг по теме.

Цель проекта — не просто выдавать задания, а вести ребёнка по школьной программе так, чтобы обучение было последовательным, наглядным и адаптивным.

---

## 1. Цели проекта

MasterKva решает сразу несколько задач:

- строит диагностику по школьной программе от 1 до 9 класса;
- выявляет слабые темы без случайных прыжков по сложности;
- подаёт обучение в визуальной, CPA-ориентированной форме;
- использует учебный материал, а не абстрактные шаблоны;
- разделяет диагностику, объяснение и практику как разные состояния системы;
- помогает ребёнку проходить тему последовательно, без перегрузки текстом.

## 2. Педагогическая модель

### 2.1 Диагностика

Диагностика должна:

- идти последовательно от младших классов к старшим;
- не перескакивать через базу;
- повышать сложность постепенно;
- при ошибке по теме давать ещё 2–5 аналогичных заданий того же уровня;
- считать тему слабой, если в 5 попытках сделано 2 ошибки;
- минимизировать подсказки;
- по возможности не показывать доску, если она может подсказывать визуально.

### 2.2 Обучение

После диагностики ученик переходит в режим обучения. Здесь важны другие принципы:

- использовать учебный материал темы;
- показывать визуализацию, соответствующую конкретной теме;
- держать минимум текста и максимум наглядности;
- использовать интерактивную доску;
- для ранней арифметики применять `number_bond`, а не универсальный CPA-шаблон.

### 2.3 Логика прогресса

Если тема освоена слабо, система не должна сразу идти дальше. Она должна:

- зафиксировать слабость;
- выдать дополнительные похожие задания;
- снова проверить понимание;
- только после этого открывать следующий шаг.

## 3. Архитектура проекта

Система уже разделена на несколько слоёв.

### 3.1 Диагностический слой

Основные файлы:

- `backend/data/diagnostic_pool.json`
- `backend/data/curriculum/canonical_curriculum.json`
- `backend/deeptutor/services/diagnostic_engine.py`

Функции слоя:

- хранение диагностических вопросов;
- привязка вопросов к темам и навыкам;
- учёт метаданных по покрытию;
- переход от диагностики к объяснению и далее к практике.

Важно: текущий `diagnostic_pool` — это пока не полноценная единая карта всей программы 1–9 классов, а ограниченный пул вопросов, который уже размечен и служит основой для расширения.
Каноническая карта учебной программы задана через `canonical_curriculum.json`; для `curriculum` используются полные `grade_N_full.json`, а компактные `grade_N.json` остаются legacy-сводками.

### 3.2 Визуальный слой

Основные файлы:

- `backend/data/visual_topic_map.json`
- `backend/deeptutor/services/visual_template_service.py`
- `frontend/components/interactive-blackboard.tsx`
- `frontend/components/visualizations/number-bond.tsx`
- `frontend/components/visualizations/question-visual.tsx`

Назначение слоя:

- каждая тема получает собственную визуальную подачу;
- ранняя арифметика идёт через `number_bond`;
- старшие темы могут использовать другие визуальные шаблоны;
- визуал соответствует учебному материалу, а не общему универсальному макету.

### 3.3 Skill-aware runtime

Основные файлы:

- `backend/deeptutor/services/skill_runtime.py`
- `backend/data/skill_registry.json`
- `backend/data/skill_contracts.json`

Этот слой позволяет:

- понимать, какая тема сейчас активна;
- различать `shadow` и `active`-режимы;
- хранить состояние навыка;
- писать runtime audit log;
- делать развитие системы более контролируемым и безопасным.

## 4. Что уже реализовано

### 4.1 Исправлено смешение диагностики и обучения

Раньше диагностика могла слишком рано сливаться с обучением. Это приводило к тому, что объяснение и следующий шаг могли появляться прямо внутри `diagnostic-mode`.

Теперь это исправлено:

- после завершения диагностики система фиксирует слабую тему;
- подбирает skill/contract и учебный контекст;
- автоматически запускает практику по найденному пробелу;
- remediation и mastery gate остаются отдельными backend-owned этапами.

### 4.2 Добавлен skill-aware runtime

Реализован thin runtime-слой, который умеет:

- резолвить текущий skill;
- различать `active` и `shadow`;
- хранить поля вроде `current_skill_id`, `current_skill_mode`, `current_topic_id`, `learning_mode_active`, `board_mode`, `mastery_status_by_skill`, `registry_resolution`;
- писать события в runtime audit log.

### 4.3 Созданы `skill_registry` и `skill_contracts`

Добавлены:

- `backend/data/skill_registry.json`
- `backend/data/skill_contracts.json`

Назначение этих файлов:

- хранить карту навыков;
- хранить контракты покрытия и модели ошибок;
- обогащать диагностические вопросы метаданными;
- дополнять текущую логику безопасным слоем, не ломая runtime.

### 4.4 Один навык переведён в `active` pilot

Навык `g2_addition_core` переведён в режим `active` как пилотный.

Это значит, что:

- остальная система остаётся в `shadow`;
- один навык уже проходит через новый runtime-путь;
- можно проверять живой сценарий без массового риска.

### 4.5 Проверен живой сценарий в браузере

Был проведён ручной E2E-сценарий, имитирующий школьника.

Проверялось:

- вход ученика;
- прохождение диагностики;
- завершение диагностики;
- автоматический переход в `practice`;
- дальнейшая практика и remediation.

Результат:

- диагностический flow работает;
- переход в практику работает;
- `g2_addition_core` корректно подхватывается;
- практика появляется в нужной фазе;
- board policy соблюдается.

## 7. Главное текущее ограничение

Полноценная единая диагностика по всей программе 1–9 классов ещё не собрана как целостная система.

Сейчас есть:

- частичные данные;
- материалы по темам;
- визуальная карта тем;
- адаптированные уроки;
- runtime-слой;
- пилотный навык.

Но требуется следующий большой шаг:

- собрать единую диагностическую карту по всем темам;
- формализовать coverage по всей программе;
- расширить правила выбора заданий;
- унифицировать визуальную подачу;
- сделать устойчивый coverage-run по всем классам.

---

## 8. Основные правила проекта

- Диагностика должна идти последовательно от младших классов к старшим.
- Нельзя перепрыгивать через базу.
- При ошибке нужно добирать аналогичные задания того же уровня.
- Если 2 ошибки из 5, тема считается слабой.
- В диагностике доска лучше выключена.
- В обучении доска должна быть включена.
- Для ранней арифметики нужен `number_bond`.
- Обучение должно идти по учебному материалу, а не по общим абстрактным шаблонам.
- Состояние навыка должно храниться явно.
- Диагностика, remediation и mastery gate должны быть разделены.
- `v1` лучше держать как простую и надёжную state machine, а не как перегруженный LLM-оркестратор.
