# Что не хватает до полноценной реализации MasterKva

Дата: 2026-06-08

## Текущий статус

Проект сейчас находится ближе к hardened MVP, чем к production-запуску для детей.

Уже закрыт важный P0-скелет:

- инструкции преподавателя сохранены в `frontend/prompts/master_kvat_system.md`;
- teacher LLM больше не должен заканчивать урок фразами вроде «хочешь ещё?»;
- добавлен stop/pause intent;
- место ребёнка сохраняется при паузе;
- remediation больше не показывает ответ следующего шага вместо текущего;
- practice fallback берёт задания из `diagnostic_pool`, если нет специального генератора;
- frontend/backend фазы синхронизированы для `remediation`, `mastery_check`, `paused`;
- image route ищет реальные textbook assets;
- targeted backend QA и frontend build проходят.

## P0: обязательно до запуска

### 1. Починить полный API/TestClient pytest-прогон

Targeted tests проходят, но полный API/TestClient-набор зависает. Это нельзя оставлять перед запуском.

Нужно:

- локализовать конкретный тест или fixture, где начинается hang;
- проверить взаимодействие `TestClient`, state file, global remediation state и async endpoint;
- добавить timeout/diagnostic logging для зависающих тестов;
- вернуть полный API test suite в стабильный release gate.

### 2. Полноценные генераторы практики и ремедиации

Сейчас для непокрытых тем fallback берёт релевантный вопрос из `diagnostic_pool`. Это лучше, чем давать чужую арифметику, но ещё не полноценное обучение.

Нужно:

- для каждого `skill_contract` создать practice generator;
- для каждого `item_family` создать remediation generator;
- обеспечить 3-5 вариантов одного навыка без повторения одного и того же вопроса;
- проверять, что слабая тема всегда ведёт к релевантной практике;
- добавить coverage test: `weak_topic -> practice -> remediation -> visual -> mastery`.

### 3. Structured output для teacher LLM

Prompt сохранён, guardrails есть, но runtime всё ещё принимает обычный текст.

Нужно перевести teacher LLM на структурированный ответ:

```json
{
  "teacher_text": "короткая реплика преподавателя",
  "pedagogical_move": "praise|hint|explain|remediate|transition|pause",
  "safety_flags": [],
  "needs_human_review": false
}
```

Backend должен:

- принимать только валидный structured output;
- использовать только `teacher_text` в UI;
- логировать `pedagogical_move`;
- отправлять на fallback при невалидном ответе;
- не давать LLM выбирать фазу, тему, mastery или следующее задание.

### 4. Полноценная история ребёнка

Сейчас есть базовый `session_status` и `learning_memory`, но не хватает настоящей педагогической памяти.

Нужно хранить:

- последние пройденные темы;
- текущую тему и навык;
- выявленные слабые темы;
- освоенные слабые темы;
- очередь следующих слабых тем;
- типичные ошибки;
- какой способ объяснения помог;
- какие подсказки использовались;
- как ребёнок отвечал;
- после какого объяснения тема стала понятнее;
- следующую тему для проверки после освоения текущей слабой темы.

### 5. Очередь слабых тем

После освоения одной слабой темы система должна не просто идти дальше, а искать следующий пробел.

Нужно:

- сохранять `weak_topic_queue`;
- при mastery текущей темы выбирать следующую слабую тему;
- если очередь пустая, запускать micro-diagnostic;
- учитывать prerequisite graph;
- не перескакивать на старшие темы, если база ещё не закреплена.

## P1: нужно для надёжного обучения

### 1. Усилить mastery gate

Текущий mastery gate полезен, но слишком простой для production.

Нужно учитывать:

- разнообразие заданий;
- правильность без подсказок;
- ошибки после remediation;
- повтор через время;
- разные `item_family`;
- confidence не как формальность, а как качество доказательства усвоения.

### 2. Полные визуализации

Generic template cards есть, но не все canonical visual types реализованы как настоящие интерактивные визуализации.

Нужно:

- реализовать визуалы для всех canonical template types;
- проверить mobile/desktop layout;
- добавить visual regression или screenshot smoke;
- убедиться, что визуал не подсказывает в диагностике, если board policy запрещает.

### 3. Safety layer для детей

Stop/pause уже есть, но нужен полный детский safety layer.

Нужно:

- фильтр персональных данных;
- реакция на self-harm/abuse/опасные темы;
- parent-safe logging;
- escalation flags;
- запрет на неучебные советы;
- policy tests для детских сценариев.

### 4. Production-хранилище вместо `user_states.json`

JSON-файл подходит для MVP, но не для нескольких детей одновременно.

Нужно:

- выбрать durable storage;
- сделать migration profile schema;
- добавить locking/concurrency protection;
- разделить runtime state и long-term student profile;
- добавить backup/export для родителя/преподавателя.

### 5. Dashboard родителя/преподавателя

Нужен понятный отчёт:

- что ребёнок прошёл;
- какие темы слабые;
- какие темы закрыты;
- где повторяются ошибки;
- что система делала для обучения;
- что рекомендуется дальше.

## P2: нужно для уверенного запуска

### 1. Полный docker/e2e smoke

Нужно проверить полный путь:

- backend стартует;
- frontend стартует;
- API URL корректный;
- картинки грузятся;
- диагностика проходит;
- слабая тема находится;
- practice появляется;
- remediation работает;
- mastery/promotion работает;
- pause/resume работает.

### 2. Нагрузочные проверки

Нужно проверить:

- несколько детей одновременно;
- параллельные записи состояния;
- отсутствие перемешивания user state;
- поведение при перезапуске backend.

### 3. Логи и метрики

Нужно логировать:

- ошибки LLM;
- structured output fallback;
- unmapped practice family;
- unmapped visual template;
- зависшие сессии;
- частые слабые темы;
- частые ошибки по item family.

### 4. Модельная стратегия

Нужно определить:

- основную teacher model;
- дешёвый fallback;
- verifier/escalation model;
- правила переключения модели;
- лимиты стоимости;
- eval suite для сравнения моделей.

## Рекомендуемый следующий шаг

Самый правильный следующий блок:

1. Починить полный test hang.
2. Перевести teacher LLM на structured output.
3. Расширить student memory и `weak_topic_queue`.
4. Добавить coverage test: каждый weak topic должен вести к релевантной практике и remediation.

Это даст максимальное снижение риска неправильного поведения ИИ перед запуском.
