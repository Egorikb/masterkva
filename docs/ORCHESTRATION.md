# Оркестрация разработки «Мастер Ква»

Версия: 2026-09-09  
Статус: подготовка к реализации  
Текущий исполнитель оркестратора: **GPT-5.6 Luna, reasoning medium**  
Следующая проверка архитектуры: **GPT-6 Astra**, когда снова станет доступен лимит.

Этот файл фиксирует, кому и в каком порядке поручать работу. Он дополняет [roadmap](/home/egor/workspace_hermes/MasterKva/docs/ROADMAP_2026-09-09.md) и [аудит](/home/egor/workspace_hermes/MasterKva/docs/PROJECT_REVIEW_2026-09-09.md). Вложения `text.txt` и `read.txt` являются исходными материалами и не переопределяют этот рабочий план.

## Правила оркестратора

1. Рабочей базой считать `ACTIVE`. Не удалять архивы и не делать reset грязного состояния.
2. Каждый агент получает одну измеримую задачу, список разрешённых путей и критерии приёмки.
3. Перед изменением агент читает всех вызывающих этот код и существующие тесты. Новые абстракции не добавлять без необходимости.
4. Два агента не редактируют один и тот же файл в одной волне. После волны оркестратор проверяет diff, тесты и контракт.
5. Модель не принимает математический ответ и не меняет прогресс. Это делает backend по проверенному контракту.
6. Любой ответ модели проходит схему и имеет запасную детерминированную реплику. Платные вызовы ребёнку включаются только после локального теста.
7. Агент не читает `.env`, ключи, профили и персональные данные. Для проверки использовать фикстуры и переменные окружения-заглушки.
8. Агент останавливается с отчётом, если критерий невозможно проверить, а не объявляет задачу выполненной по одному зелёному тесту.

## Назначение моделей

| Модель | Назначение | Что ей не поручать |
|---|---|---|
| GPT-6 Astra | Архитектурные решения, спорные изменения, финальный gate и пересмотр плана | Массовые механические исправления |
| GPT-5.6 Sol | Сложный backend, state machine, безопасность, конкуренция, педагогические edge cases | Большие однотипные миграции |
| GPT-5.6 Terra | Основная реализация frontend/API/голоса и интеграции | Самостоятельное утверждение учебных эталонов |
| GPT-5.6 Luna | Инвентаризация, тестовые матрицы, JSON-проверки, документация, повторяемый QA | Изменение смысла заданий и архитектурные решения без ревью |
| GPT-5.5 | Независимое ревью при нехватке Sol | Параллельное редактирование тех же файлов |

Текущий режим Luna medium подходит для подготовки и безопасных массовых проверок. Он не считается окончательным решением по архитектуре; спорные пункты помечаются `ASTRA_REVIEW`.

## Очередь реализации

### Волна 0 — уже подготовлена оркестратором

- Сформулирован единый MVP: четыре навыка арифметики, один экран задания, голосовой ответ ребёнка и озвучка преподавателя.
- Зафиксированы дефекты проверки ответов, remediation, визуалов, хранения и контента в аудите.
- Определены публичные источники тарифов и базовая смета: ориентир 700 ₽ на ребёнка в неделю при одном коротком голосовом обмене в минуту; это не включает сервер и разработку.
- Код приложения в этой волне не менялся.

### Волна 1 — правильность backend

**Исполнитель:** Sol, reasoning high.  
**Пути:** `ACTIVE/backend/deeptutor/services/practice_engine.py`, `remediation_engine.py`, `diagnostic_engine.py`, `api/routers/plugins_api.py`, соответствующие тесты.  
**Задача:** типизированная проверка ответа, отдельные действия `answer/hint/rephrase`, завершение remediation, защита от двойного учёта запроса.  
**Приёмка:** `1/2` не равен `12`, `1.5` не равен `15`, `3 см` не равен `3 м`; подсказка не портит статистику; после трёх неверных ответов нет тупика; тесты воспроизводят каждый найденный дефект.

### Волна 1 — состояние и хранение

**Исполнитель:** Terra, reasoning high.  
**Пути:** `ACTIVE/backend/deeptutor/services/student_profile_store.py`, модели API, миграция хранения и тесты.  
**Задача:** SQLite с транзакциями, профили детей, idempotency, pause/resume и отчёт из попыток.  
**Приёмка:** перезапуск сохраняет шаг; два профиля не смешиваются; повтор HTTP-запроса не удваивает попытку; существующий API-контракт не получает скрытых полей, смысл которых восстанавливает frontend.

### Волна 1 — корпус и контракты данных

**Исполнитель:** Luna, reasoning medium.  
**Пути:** `ACTIVE/backend/data/`, только отдельные валидаторы в `docs/audit/` или `scripts/`.  
**Задача:** карта стабильных `skill_id → task_id → version`, список конфликтов и пакет из четырёх навыков; найти структурные ошибки, не исправляя математику без педагога.  
**Приёмка:** отчёт воспроизводим одной командой; каждый материал имеет эталон, тип ответа, визуальную политику и статус ручной проверки; случайная тема из RAG не попадает в пакет.

### Волна 2 — детский интерфейс

**Исполнитель:** Terra, reasoning medium/high.  
**Пути:** `ACTIVE/frontend/`, контракты только по согласованной схеме backend.  
**Задача:** одна задача на экране, крупные действия, явный `visual: null`, pause/resume, доступный ввод без голоса, панда не перекрывает сцену.  
**Приёмка:** браузерный smoke на 390×844, 768 и 1024 px; ребёнок начинает и завершает короткий сценарий без помощи взрослого по интерфейсу.

### Волна 2 — голос и модельный шлюз

**Исполнитель:** Sol, reasoning medium/high.  
**Пути:** backend adapter, конфигурация провайдера, voice-компонент и тесты; ключи не добавлять в репозиторий.  
**Задача:** SpeechKit STT/TTS через backend, подтверждение неоднозначного распознавания, остановка/повтор озвучки, Qwen structured output, timeout и fallback.  
**Приёмка:** ошибка распознавания не считается математической ошибкой; аудио можно остановить; модель не меняет состояние занятия; логируются токены, секунды, символы, повторы и стоимость.

### Волна 2 — интеграционный QA

**Исполнитель:** Luna, reasoning medium.  
**Пути:** новые тесты и `docs/audit/`, без изменения production-логики.  
**Задача:** матрица ошибок, подсказок, повторов, недоступности API, перезапуска, двух профилей и мобильных экранов.  
**Приёмка:** каждый сценарий имеет ожидаемый ответ, фактический результат и ссылку на исправление; отдельно отмечены случаи, которые требуют ручного запуска с микрофоном.

## Ворота Astra

После волн 1–2 перед семейным пилотом Astra повторно проверяет:

- один ли источник истины управляет переходами занятия;
- не может ли модель раскрыть ответ или изменить оценку навыка;
- не смешиваются ли дети и не теряются ли попытки;
- соответствует ли визуал текущему заданию;
- выдерживает ли контракт отказ LLM/STT/TTS;
- оправдан ли Qwen 3.8 Flash против Qwen 3.7 Flash на отложенных русских сценариях;
- не превышает ли фактический расход бюджет 700 ₽/неделю при базовой нагрузке.

Если Astra недоступна, Luna выполняет только проверку по заранее записанным критериям и оставляет `ASTRA_REVIEW`, а не закрывает архитектурные вопросы своим предположением.

## Шаблон задачи агенту

```text
Контекст: MasterKva, рабочая база ACTIVE.
Цель: <один измеримый результат>.
Разрешённые пути: <точные файлы/каталоги>.
Нельзя: читать ключи и персональные данные; менять чужие пути; добавлять зависимость без причины.
Проверка: <команды и сценарии>.
Приёмка: <наблюдаемые условия>.
В отчёте: изменённые файлы, тесты, ограничения и нерешённые вопросы ASTRA_REVIEW.
```

## Формат отчёта волны

```text
Статус: READY | BLOCKED | ASTRA_REVIEW
Изменено: <файлы>
Проверено: <команды и результат>
Риски: <только подтверждённые>
Следующий владелец: <модель/роль>
```
