MasterKva — описание проекта и финальный бриф

## Что это за проект
MasterKva — платформа обучения математике для 1–9 классов. Цель проекта — не просто выдавать задания, а строить полноценный учебный путь:
- диагностика уровня ученика;
- выявление слабых тем и навыков;
- точечное объяснение по учебному материалу;
- практика на похожих заданиях;
- проверка закрепления навыка;
- переход дальше только после mastery gate.

Проект использует учебные материалы, визуальные шаблоны и интерактивную доску. Для ранней арифметики особенно важен формат `number_bond`, а не общий CPA-шаблон.

## Финальная архитектурная позиция
### Что мы берём за основу
Берём план GPT-5.5 как основу, но дополняем его отдельным слоем **Skill Contract**.

### Итоговая структура
1. Skill Registry
2. Skill Contract
3. Assessment Engine
4. Learning Engine
5. Visual Engine
6. LLM Tutor Layer

### Что хранит Skill Registry
- skill_id
- grade
- domain
- topic
- prerequisites
- next_skills

### Что хранит Skill Contract
- coverage_status
- diagnostic rules
- remediation mapping
- visual template
- board policy
- mastery gate
- error model

## Что уже работает
### Диагностика
- идёт по темам и навыкам от простого к сложному;
- после ошибки даёт несколько похожих задач того же уровня;
- если ошибок много, тема помечается как слабая;
- в диагностике доску лучше отключать.

### Обучение
- после диагностики система переходит в обучение только по найденной слабой теме;
- здесь доска включена;
- визуализация должна соответствовать теме и учебному материалу;
- объяснение короткое, наглядное и по шагам.

### Уже исправленное поведение
- исправлен конфликт между диагностикой и практикой;
- после завершения диагностики система ждёт явного продолжения;
- проверены сценарии через Playwright/Chromium;
- подтверждено, что чат и доска синхронизированы;
- для локальной QA на этой машине рабочий обход — Chromium с `--no-sandbox`.

## Что уже есть в проекте
- `backend/data/diagnostic_pool.json` — текущий диагностический пул вопросов;
- `backend/data/visual_topic_map.json` — карта тем к визуальным шаблонам;
- `backend/data/curriculum_detailed/` — детализированная программа;
- `backend/data/lessons/*_ru_adapted.json` — адаптированные уроки;
- backend-логика уже подправлена для правильного завершения диагностики;
- есть тесты и E2E-сценарии.

## Что ещё не идеально
- текущий диагностический пул слишком маленький для полноценной диагностики всей программы;
- нужен более строгий механизм выбора следующего вопроса;
- нужен понятный loop: ошибка -> похожие задачи -> проверка -> слабая тема -> обучение;
- нужны более чёткие правила для включения/выключения доски по фазам;
- нужна более надёжная структура данных для навыков и тем;
- нужен способ масштабировать систему, не ломая школьный учебный сценарий.

## Что сказали внешние модели
### Perplexity
- не переусложнять LLM-слой;
- для v1 держать простую state machine: `diagnose -> remediate -> practice -> promote`.

### GPT-5.5
- нужен `skill_registry`;
- диагностика, remediation и mastery gate не должны смешиваться;
- backend должен решать переходы;
- нужен `coverage_status` по каждому skill;
- current diagnostic pool слишком мал для полной диагностики 1–9.

## Что я добавил от себя
Нужно ввести отдельный слой **Skill Contract** над `skill_registry`.

Он должен содержать:
- `coverage` — что покрыто и в каком статусе;
- `error_model` — типичные ошибки и что делать дальше;
- `board_policy` — off / limited / on;
- `mastery_gate` — как считается освоение;
- `visual_policy` — какой шаблон допускается.

## Что особенно важно для v1
- не делать LLM источником образовательной истины;
- держать backend владельцем логики;
- не смешивать диагностику и урок;
- не пытаться сразу покрыть всю математику 1–9 одинаково качественно;
- сначала закрыть ядро 1–4 классов, потом расширять 5–9;
- визуалы использовать как support layer, а не как источник правил.

## Что нужно от внешней модели
Нам нужен не пересказ, а критичный архитектурный суд:
- что упростить;
- что добавить;
- что менять сразу;
- что отложить;
- какие риски и failure modes самые вероятные;
- есть ли более сильная архитектура.
